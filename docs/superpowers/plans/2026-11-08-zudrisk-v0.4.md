# ZudRisk v0.4 (2026/27 outlook + as-of hindcasts) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put the first 2026/27 dzud outlook on the site, using data through October 2026. Show beside it an honest measure of what an outlook at that stage is worth: the same six past winters, re-scored with only the data each stage would have had.

**Architecture:**
- Pull scoring out of `indicators.main` into `compute(year, as_of)`, so a winter can be scored at any stage without writing files.
- `asof.py` scores the six hindcast winters at six stages and validates each stage the way v0.2 validates a whole winter.
- `outlook.py` scores the coming winter at its latest complete stage, and refuses a stage whose data has not landed.
- Recent ERA5-Land and NDVI months are fetched as they appear.

**Tech Stack:** Unchanged. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-08-zudrisk-design.md`: §2 goal 4, §4.5 "Hindcast vs outlook", and the §7 v0.4 row. Plans v0.1–v0.3 are in this folder, and their Global Constraints still hold.

## Decision for the user (asked with this plan)

**Recommended: cold comes from ERA5-Land 2 m temperature, not NASA POWER, from v0.4 on.**

Why:
- On 2026-11-08, POWER's monthly T2M ends at September 2026. It runs about 5–6 weeks behind; ERA5-Land monthly means already have October.
- With POWER, the "through November" outlook could not run before mid-January.
- The spec already moved snow off GLDAS for latency (§4.3). This applies the same rule to cold, decided now, before any number is seen.
- Bonus: ERA5-Land is a 0.1° grid instead of about 0.5°, so neighbouring soums stop sharing one cold value (spec §8 risk).

Cost:
- All six hindcasts are re-scored, so their published ρ change. Old and new are reported side by side, untuned.
- `power.py` stays in the repo but leaves the score.

If you prefer to keep POWER, Task 2 is dropped, and each outlook stage waits until POWER has its month.

## Global Constraints

Everything in the v0.1–v0.3 Global Constraints applies, plus the rules below.

**Stages.** A stage is named by the last month of data it holds. It is scored as of that month's last day.

| Stage | as_of | Indicators scored |
|---|---|---|
| `oct` (pre-winter) | 31 Oct Y | summer, pressure |
| `nov` | 30 Nov Y | + Nov |
| `dec` | 31 Dec Y | + Nov–Dec |
| `jan` | 31 Jan Y+1 | + Nov–Jan |
| `feb` | last day of Feb Y+1 | + Nov–Feb |
| `mar` | 31 Mar Y+1 | the full hindcast, identical to the v0.3 run |

A stage runs only when every month it holds has landed. For ERA5-Land that is about 5 days after the month ends.

**No look-ahead.**
- Pressure uses the latest census published by the stage's as_of date. Ruling: census Y, counted in December Y, is used only from 1 Feb Y+1; earlier stages use census Y−1.
- The NDVI summer is Jul–Aug Y at every stage.
- Baseline winters see the same months, through the existing `shift_as_of`.
- The validation target is unchanged: losses in Y+1 ÷ census Y.

**The outlook is labelled.**
- Every outlook view on the site says it is an outlook for a winter still under way.
- It shows the as-of validation of its own stage, never that of the full winter.
- Indicators not yet observed are named "not observed yet", never "missing".

**Separate index.** The outlook never enters `winters.json`, the hindcast index that `compare.main` and `hindcast` read. It has its own `outlook.json`.

## Data (checked live 2026-11-08)

| Source | Available | Needed now (stage `oct`) |
|---|---|---|
| NSO stock, losses | through 2025, already in `livestock.csv` | census 2025 ✓ |
| MOD13C2 NDVI | through 2026-10 (VJ113C2 and VNP13C2 also exist) | Jul–Aug 2026 ✓, so VIIRS is not needed this winter |
| ERA5-Land monthly | through 2026-10, per the constraints endpoint | none for `oct`; Nov lands about 5 Dec |
| NASA POWER T2M | through 2026-09 | — (see the decision above) |

**ERA5-Land requests.** The CDS takes year × month as a product, so a month that is not yet published fails the whole job. Fetch in two kinds of job:
- **History job:** 2001–2024 × {01, 02, 03, 11, 12} × four variables (`snow_depth`, `snow_density`, `snow_cover`, `2m_temperature`). Cached at `data/raw/era5_land_2001_2024.nc`.
- **Recent jobs (2025 on):** one per year, holding only the months the constraints endpoint lists. Cached at `data/raw/era5_land_<year>_<last mm>.nc`, so a new month makes a new file.

`t2m` arrives in kelvin and is stored as °C.

## File structure

```
pipeline/http.py        + cds_months(dataset, year, variable, auth=None) -> list[str] (constraints endpoint)
pipeline/era5.py        history job + per-year recent jobs; VARS gains t2m -> t2m_c; read_fields merges files
pipeline/ndvi.py        summers through the latest July-August MOD13C2 has
pipeline/indicators.py  compute(year, as_of) -> dict[pcode, row]; cold() from soum t2m series; census_year(year, as_of)
pipeline/asof.py        STAGES; six winters x six stages -> data/derived/asof_validation.json + site/data copy
pipeline/outlook.py     --through YYYY-MM: completeness check, compute, site/data/outlook_<label>.geojson + outlook.json
pipeline/hindcast.py    runs asof after compare
site/app.js, index.html outlook entry in the selector, banner, stage skill table, "not observed yet"
README.md               the monthly re-run command
```

## Review Focus

1. **A stage whose month has not landed** (for example ERA5 Nov before about 5 Dec). `outlook` must exit non-zero, naming the source and month. It must never score with fewer indicators than its stage's validation used. Covered by an `outlook` check.
2. **Census look-ahead.** `census_year(2023, date(2024, 1, 31)) == 2022` and `census_year(2023, date(2024, 2, 29)) == 2023`. On real data, the `oct` stage's z_pressure for 2023 comes from census 2022. Covered by an `indicators` check.
3. **The `mar` stage equals the hindcast.** `asof` at `mar` must reproduce each winter's v0.4 hindcast risk exactly, so the stages and the hindcast cannot drift apart. Covered by an `asof` check.
4. **The outlook is kept out of the hindcast index.** After `outlook` runs, `winters.json` is unchanged and `compare.main()` still runs. Covered by an `outlook` check.
5. **A merged ERA5 month present twice** (in the history file and a recent file, or in two recent files of one year). The newest file wins, with no duplicate rows. Covered by an `era5` check.

## Rulings recorded in this plan

- **Census publication date.**
  - Ruling: census Y counts as available from 1 Feb Y+1.
  - Why: NSO's release date was not verified, and the later date cannot leak future data.
  - Cost if wrong: if NSO publishes earlier, the dec and jan stages use an older census and understate their skill slightly.
- **Stages are named by data month, not by run date.**
  - Ruling: the spec's "1 Dec" outlook becomes stage `nov`, run when November lands (about 5 Dec).
  - Why: on 1 Dec itself, November is not published anywhere, so a "1 Dec" stage holding November would be look-ahead.
  - Cost: no loss of skill; the labels just come a few days after the spec's dates.
- **More stages than the spec named.**
  - Ruling: stages are oct, nov, dec, jan, feb and mar, not only 1 Nov, 1 Dec and 1 Jan.
  - Why: the spec also asks for monthly re-runs through March, and each needs its own validation.
  - Cost: three more validation rows.
- **VIIRS not built.**
  - Ruling: VIIRS continuity is deferred.
  - Why: MOD13C2 still has Jul–Aug 2026; summer 2027 is the first that may need VIIRS.
  - Cost: none this winter.
